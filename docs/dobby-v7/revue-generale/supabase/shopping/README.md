# C07 — Disponibilité partagée : lot manuel

Statut **ATTENTE_UTILISATEUR**. Aucune connexion ni exécution Supabase distante n’a eu lieu. Le candidat exact d’installation, de vérification et de retour arrière a été testé uniquement sur PostgreSQL 17.7 local, dans un conteneur sans réseau ni port et avec des données fictives. Les contrôles .001, bornes/NaN/Infinity, révision périmée, ancien PATCH, répétition d’installation et refus d’un type incompatible passent (`../tests/run-shopping-local.py`). Cette fixture ne certifie ni les RLS/RPC réelles ni le catalogue distant ; les tests HTTP sont également synthétiques.

**Reprise des réserves techniques du 13 novembre 2026 : une seule action initiale.** Utiliser le [diagnostic regroupé en lecture seule](../../../reserves-techniques/serveur/00-diagnostic-regroupe.sql) et son [mode d’emploi](../../../reserves-techniques/serveur/README.md). Ne pas rejouer l’installation parce que ce dossier existe. Si le catalogue est déjà conforme, aucune installation C07 n’est nécessaire. Si une absence est confirmée et que les autres préconditions concordent, le candidat révisé ci-dessous peut être examiné pour une application manuelle ciblée. Un contrat différent impose un arrêt et une adaptation à la sortie réelle, sans conversion de colonne ni remplacement de contrainte automatique. Le [bilan C07 actuel](../../../reserves-techniques/COURSES-C07.md) précise ces branches. `00-preflight.sql` reste une annexe historique, pas un deuxième diagnostic à exécuter par défaut.

La migration proposée ajoute seulement `public.dobby_v2_grocery.at_home_quantity numeric NOT NULL DEFAULT 0`, sans échelle fixe pour conserver `0.001 kg`. Les disponibilités des anciennes lignes commencent à zéro. Aucun article, achat, reçu d’import ou état local n’est supprimé ou copié automatiquement. La contrainte autorise de 0 à 999999 et exclut NaN/Infinity ; elle ne lie pas la valeur à `quantity`, pour préserver les PATCH des anciens clients qui omettent le champ.

Le vérificateur révisé refuse les contraintes de même nom qui ne sont pas des `CHECK` validés avec l’expression PostgreSQL canonique `((at_home_quantity >= (0)::numeric) AND (at_home_quantity <= (999999)::numeric))`. Une recherche de sous-chaînes pouvait accepter à tort un `OR` ; ce faux positif a été reproduit puis corrigé. Une autre écriture, même potentiellement équivalente, demande un examen manuel ; elle n’est ni réécrite ni annoncée conforme automatiquement. Les cinq cas ciblés de `../tests/run-shopping-constraint-guard-local.py` passent sur PostgreSQL 17.7 fictif sans réseau.

Référentiel d’examen et d’application **uniquement après ce diagnostic**, dans le seul projet personnel DOBBY :

1. À partir du diagnostic regroupé, confirmer le contrat existant (`id`, `household_id`, `quantity`, `unit`, `checked`, `revision`, `deleted_at`), les politiques par foyer, les permissions parent/enfant et le mécanisme de révision CAS. Examiner les corps des triggers : un UPDATE portant seulement sur `at_home_quantity` doit augmenter `revision`. Une simple présence de trigger ne prouve pas ce comportement. Si une de ces conditions échoue, arrêter et corriger séparément ; ces scripts ne changent ni RLS ni autorisations. Avant toute intervention conditionnellement retenue, sauvegarder le schéma, les politiques, les fonctions/triggers et les données avec la procédure habituelle.
2. Si la colonne existe déjà, confirmer le type numeric sans échelle fixe, le défaut 0, NOT NULL, les contraintes et les valeurs déjà enregistrées. Le script s’arrête devant un contrat différent ; ne pas convertir ou réécrire ces données aveuglément. Confirmer la définition exacte de toute contrainte portant le même nom avant installation.
3. Appliquer [01-install.sql](01-install.sql) sur cette base isolée. Il utilise une transaction et un timeout de verrouillage de 5 secondes. Le rechargement de schéma PostgREST fait partie du candidat. Si le rôle utilise des grants par colonne, préparer séparément l’ajout strict des permissions appropriées ; aucune élévation n’est réalisée implicitement.
4. Exécuter [02-verify.sql](02-verify.sql). Résultat attendu : `availability_metadata_verified`, sans exception. Cette vérification porte sur les métadonnées et ne certifie ni les contrôles d’accès ni les triggers. Sur les seules lignes du foyer synthétique de test, tester l’écriture de `0`, `200` et `0.001` kg ; vérifier le rejet de `-1`, `1000000`, `NaN` et `Infinity`. Vérifier la hausse de révision et le refus d’un PATCH à ancienne révision, sans toucher aux comptes historiques.
5. Recette réelle A/B avec deux comptes synthétiques du même foyer : besoin 500 g, A déclare 200 g, B reçoit 200/300 ; A corrige puis annule ; tout disponible reste un non-achat. Vérifier hors ligne/rechargement puis reconnexion, modifications concurrentes avec résolution explicite, unités compatibles, import plat + dessert idempotent, suppression/clôture limitée aux achetés, ancien client qui omet la colonne, refus des écritures hors foyer et des écritures enfant non autorisées. Aucun test fixture n’équivaut à cette recette.
6. Uniquement après examen humain de ces preuves, répéter sauvegarde, préflight, installation, vérification et recette sur le projet personnel voulu. Ne jamais utiliser un projet professionnel Portenart. Recharger les clients ; la sonde native doit confirmer la colonne avant d’autoriser la déclaration partagée.

En l’absence de colonne, les erreurs `42703`/`PGRST204` activent un gate explicite. La liste reste utilisable pour les achats ordinaires, les articles sont conservés et une déclaration maison partagée est refusée. Une erreur réseau ou de permissions n’est jamais interprétée comme une absence de colonne. L’interface conserve l’erreur réelle ; Menu → Paramètres conserve les commandes de synchronisation et de copie locale.

Retour arrière : [03-rollback.sql](03-rollback.sql) décrit et vérifie le retour applicatif en conservant la colonne additive et ses valeurs. Ne pas supprimer la colonne pour revenir au client précédent : ses PATCH omettent le champ. Une transaction d’installation qui échoue avant COMMIT s’annule entièrement. Toute suppression ultérieure de la colonne est une autre opération destructive, exclue de ce lot.
