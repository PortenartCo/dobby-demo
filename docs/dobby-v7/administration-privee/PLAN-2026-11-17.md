# Administration privée DOBBY — plan d’implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Réserver les accès DOBBY aux seules personnes approuvées et rendre leur gestion quotidienne possible dans une console propriétaire.

**Architecture:** Autorisation centrale en base, indépendante du rôle familial ; RLS et guards RPC/Storage cumulatifs. Petite API Edge d’administration, Auth Admin isolé, liaison familiale et synchronisation V7 réutilisées.

**Tech Stack:** JavaScript/ES modules existants, Supabase Auth/Postgres/Storage/Edge Functions ; Node 22 pour les vérifications existantes. Pas de moteur IA supplémentaire.

**Spec:** [CONCEPTION-2026-11-17.md](CONCEPTION-2026-11-17.md). **Proposition non approuvée pour exécution distante.**

**Publication pour revue :** reprise documentaire du commit local `da11ac124be3d7abfc133a884f5751d11cf26552`, depuis `origin/main` à `a637b8f9208a44479ccd87b82ba9d09d66cec75e`. Les 13 scénarios ci-dessous sont à exécuter pendant une future mission ; ils ne sont pas déclarés réussis. Les 83 tests d’accès précédemment consignés n’ont pas été relancés pour cette publication. Les contrôles de publication portent sur la confidentialité, le périmètre des deux fichiers, les liens, la matrice et `git diff --check`.

## Global Constraints

- Projet personnel exclusivement `dobby-family-sync` / `pqcdkrwljgvgagzwrcmg` ; jamais un projet Supabase professionnel Portenart.
- Préserver les deux comptes familiaux, leurs identifiants, foyers, profils TEXT, données, ledger et files locales ; conserver tout autre compte éventuel sans auto-autorisation.
- Identité propriétaire = UUID serveur ; aucune clé administrative au navigateur, aucun droit propriétaire implicite sur les contenus d’autres familles.
- Suspension effective sous JWT valide ; gardes maintenues au rollback ; aucune suppression/réinitialisation et aucun ancien installateur rejoué.
- Inscriptions publiques fermées seulement après fonctionnement et tests du circuit d’invitation ; pas d’ouverture implicite des gates F08/F09/V3.
- Développement local autorisé seulement dans la future mission ; tout changement distant requiert les validations énumérées dans la conception.

## Review Focus

1. Fonction SECURITY DEFINER/alias/reçu échappant à RLS : refus avant tout résultat pour l’utilisateur suspendu ou non approuvé (lot 2, T06/T08).
2. Autre compte ou e-mail changé : aucun rattachement du mauvais UUID ; le lien Auth reste un secret permettant d’endosser l’identité invitée s’il est partagé (lot 3, T03/T04).
3. Réponse tardive, suspension et écriture concurrentes : aucun résultat/réessai d’un ancien acteur ; ordre de verrous cohérent (lots 2/4, T07/T11).
4. Storage signé/public et copies : passerelle par défaut et anciens liens/caches traités avant ouverture ; pas de téléchargement après suspension par un autre chemin (lot 2, T09).
5. Ancien compte/session/cache : accès A/B conservé, compte non lié non autorisé, aucune perte ni transfert silencieux de foyer (lots 1/4/5, T10/T11).

## Lot 3 — approbation nominative et livraison Auth

**Créer :** `supabase/functions/dobby-access-admin/index.ts`, `_shared/dobby-auth-admin.ts`, `_shared/dobby-admin-validation.ts`, `tests/private-access/{admin-api,invite-delivery}.test.mjs`. Adapter les nouvelles migrations et `essai-stitch-v5-famille/family-access.mjs` pour le callback/consommation.

**API fermée proposée** (POST JSON, Bearer JWT, `operationId`, `expectedRevision` pour mutation) : `listAccess({cursor})`, `invite({email,purpose,householdId?,memberId?})`, `decide({admissionId,decision:'approve'|'reject'})`, `setStatus({userId,status:'active'|'suspended',confirmed:true})`, `revokeAdmission({admissionId})`, `listDecisions({cursor})`. Les UUID cibles sont des ressources validées, jamais l’identité de l’administrateur. Pagination et projection explicite des champs Auth retournés, sans `user_metadata` ou données privées.

**RPC utilisateur proposées :** `dobby_access_request_family_account(p_email,p_kind,p_member_id,p_operation_id)` crée une demande dans le seul foyer canonique du demandeur ; `dobby_access_accept(p_admission_id,p_profile,p_operation_id)` consomme celle du seul sujet authentifié. `p_profile` contient les champs personnels validés par le validateur V7 pour nouveau foyer/adulte ; il vaut NULL pour l’enfant existant. La transaction prépare ce profil et active/rattache le compte ensemble ; aucun accès provisoire n’est visible avant commit. Elle refuse un statut suspendu ou une génération ancienne, même sur rejeu. Extension des invitations V7 avec admission approuvée/UUID cible, mêmes transactions/reçus de rattachement ; les anciens créateurs libres refusent le chemin non approuvé.
